# Results — Daily Merchant Risk Reporting Pipeline

## Overview

A 3-stage Delta Lake pipeline built with Python and the `accrue` package:

```
Postgres  ──bronze──▶  Bronze Delta  ──silver──▶  Silver Delta  ──gold──▶  Gold Delta  ──▶  Postgres
(source)                (raw copy)                 (cleaned)                (aggregated)     (serving)
```

To install the package:
* Create and activate a virtual environment using python 3.11 or later
* Install the package: `pip install -e datalake`

Each stage is a standalone Python script runnable via the CLI:

```bash
python -m accrue.datajobs.bronze
python -m accrue.datajobs.silver
python -m accrue.datajobs.gold   # also writes back to Postgres
```

## Assumptions

1. **`schema.sql` is always run first.** The pipeline assumes `merchant_daily_risk_reports` (and the three source tables) already exist in Postgres. The Gold sync step uses `TRUNCATE + INSERT`, not `CREATE TABLE`.

2. **`payment_events` and `audit_logs` are append-only.** Once an event is written it is never mutated — only new rows are appended. Deduplication is based on `id` + latest `created_at`.

3. **`checkout_payments` is mutable.** A checkout record can be updated post-creation (e.g. `dispute_status`, `refund_amount`). The Silver layer uses last-write-wins semantics via `META_DATA_UUID` (content hash) to select the most recent version.

4. **`report_date` is derived from `created_at`.** There is no explicit report date in the source data. We normalize `created_at` to midnight UTC as the partition key for daily aggregation.

5. **Monetary amounts are in the same currency.** No FX conversion is applied.

6. **`total_refunded_amount` comes from `payment_events` REFUNDED events**, not `checkout_payments.refund_amount`. The event log is the authoritative ledger; the checkout record's `refund_amount` field is informational.

7. **Business-level deduplication is out of scope.** The pipeline suppresses *technical* duplicates (identical bytes, same `META_DATA_UUID`). Two rows representing the same logical payment but arriving with different `id` values are treated as separate events — this is the correct behaviour for an append-only event log where each insertion gets a unique ID.

## Quality Checks & Invariants

Quality rules are enforced inside each transformer's `validate()` method, applied *after* transformation so they test the output, not the raw input.

### Silver layer

| Table | Rule | Action on failure |
|-------|------|-------------------|
| `payment_events_clean` | `id` unique | `ValueError` |
| `payment_events_clean` | `amount >= 0` | `ValueError` |
| `payment_events_clean` | `event_type` ∈ `{AUTHORIZED, CAPTURED, REFUNDED, DISPUTED}` | `ValueError` |
| `checkout_payments_clean` | `id` unique | `ValueError` |
| `checkout_payments_clean` | `captured_amount <= amount` | `ValueError` |
| `checkout_payments_clean` | `refund_amount >= 0` | `ValueError` |
| `audit_logs_clean` | `id` unique | `ValueError` |
| `audit_logs_clean` | `action` ∈ `{FRAUD_FLAGGED, REVIEW_COMPLETED, DISPUTE_OPENED, DISPUTE_RESOLVED}` | `ValueError` |

### Gold layer

| Rule | Action on failure |
|------|-------------------|
| No duplicate `(merchant_id, report_date)` pairs | `ValueError` |
| All amount columns `>= 0` | `ValueError` |
| All count columns `>= 0` | `ValueError` |
| All required columns present | `ValueError` |

## Idempotency

Every stage is **fully idempotent** — running the pipeline multiple times produces the same result.

| Stage | Write mode | Idempotency mechanism |
|-------|------------|-----------------------|
| Bronze | `append` (incremental) / `overwrite` (full reload) | Watermark prevents re-reading already-seen rows; `META_DATA_UUID` deduplication prevents duplicate inserts |
| Silver | `overwrite` | Always recomputed from the full Bronze table |
| Gold Delta | `overwrite` | Always recomputed from all three Silver tables |
| Gold → Postgres | `TRUNCATE + INSERT` | Table is always replaced with the exact Gold Delta snapshot |

## Edge Case Handling

### 1. Technical duplicates (same `META_DATA_UUID`)

**Scenario:** Bronze incremental replication overlaps a time window and re-delivers the exact same row.

**Handling:** `_drop_exact_duplicates()` in Silver removes rows sharing a `META_DATA_UUID` (content hash generated by the Bronze replicator), keeping exactly one copy.

### 2. Duplicate IDs (same `id`, different rows)

**Scenario:** A retry at the source system creates a second row for the same event ID (e.g. with a corrected amount).

**Handling:** `_dedup_keep_latest(pk_col='id', ts_col='created_at')` keeps the row with the latest `created_at`, ensuring the most recent version of each event survives.

### 3. Out-of-order events

**Scenario:** A `CAPTURED` event arrives in Bronze before its corresponding `AUTHORIZED` event (due to late delivery or replication lag).

**Handling:** Events with distinct `id` values are independent rows — both are preserved in Silver. Gold aggregates by `event_type`, so `total_authorized_amount` and `total_captured_amount` are always computed independently from all events on that date, regardless of arrival order.

### 4. Partial captures

**Scenario:** A merchant partially captures an authorization (e.g. authorized $150, first capture $50, second capture $30).

**Handling:** Each CAPTURED event has its own `id` and survives Silver deduplication. Gold sums all CAPTURED amounts per `(merchant_id, report_date)`, so `total_captured_amount = 80` — correctly reflecting the partial fill.

### 5. Disputes after capture

**Scenario:** A `dispute_status` appears on a `checkout_payments` record after the payment lifecycle has completed.

**Handling:** `checkout_payments` is treated as mutable. Silver uses last-write-wins (max `META_DATA_UUID`) to always keep the latest version of each checkout record. Gold counts rows where `dispute_status IS NOT NULL AND dispute_status != ''` as disputed, regardless of when the dispute was raised.

### 6. Fraud signals

**Scenario:** Multiple `FRAUD_FLAGGED` entries arrive for the same merchant on the same day.

**Handling:** `audit_logs` is append-only. Silver adds an `is_fraud_signal` boolean (`action == 'FRAUD_FLAGGED'`) and deduplicates only on `id`. Gold sums `is_fraud_signal` per `(merchant_id, report_date)` — every distinct fraud signal event is counted.

### 7. Merchants with no payment events on a given day

**Scenario:** A merchant has a dispute or fraud signal on a day where no payment events exist.

**Handling:** Gold uses a full outer join across the three Silver aggregations, filling missing metrics with 0. A merchant with fraud signals but no payment events still appears in the report with `total_authorized_amount = 0` and `fraud_signal_count > 0`.

## Testing

### Unit tests (29 total, no infrastructure required)

```bash
venv/bin/python -m pytest datalake/src/test/ -v
```

Covers all edge cases listed above with pure in-memory pandas DataFrames.

### SQL integration tests (6 assertions against live Postgres)

Run after loading all data and executing the full pipeline:

```bash
bash ddl/load_data.sh
bash ddl/load_edge_cases.sh
venv/bin/python -m accrue.datajobs.bronze
venv/bin/python -m accrue.datajobs.silver
venv/bin/python -m accrue.datajobs.gold
psql -f tests/template_edge_cases.sql
```

Each query in `template_edge_cases.sql` returns **1–2 rows on success, 0 rows on failure**.
